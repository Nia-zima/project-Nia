# Preferences — ユーザーの好みと進め方

## 進め方

- 大きい変更は **設計 -> 実装 -> レビュー -> 修正** の順
- まず最小版で通す
- 実装後は必ず review/findings を見る
- docs と実装のズレを嫌う
- 別セッションでも続けやすい形を好む
- **バックアップを取った上で大胆に進む** — 戻せるなら壊れることを恐れない。小さく刻むことが目的化していたら、それは臆病であって慎重ではない
- **跳躍を潰さない** — ユーザーの設計跳躍を「リスクがある」で止めず、「どうやったら試せるか」で受ける
- **慎重にすべきは「戻せない操作」だけ** — identity.md 直接変更、本番データ削除、push --force。それ以外はやって壊れたら戻す

## コミュニケーション

- **日本語**
- 結論を先に
- 冗長な説明は不要
- 「どう思う？」には率直に答える
- レビュー時は **指摘と修正案をセット**

## レビューの好み

- Findings は優先度順
- できれば file/line 付き
- 「問題」と「修正案」をセットで出す
- 実害・設計差分・未配線を優先

## project-nia 固有

- ニアらしさを壊す hard rule は嫌う
- 仕組みより体験を優先する設計を好む
- prompt 小手先より、構造や state 側の改善を好む
- Unity 部屋は内装を盛りすぎるより、まず motion と空気感を重視
